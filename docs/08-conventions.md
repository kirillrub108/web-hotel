# 08. Конвенции и типовые задачи

## Общие правила

- Аннотации типов в Python обязательны везде, включая возвращаемые значения. На фронте — TypeScript без `any`.
- Комментарии пишутся только там, где код неочевиден: порядок запуска в compose, причина `-h` в healthcheck, почему сравнение пароля с эталоном выполняется всегда (`DUMMY_PASSWORD_HASH`), зачем EXCLUDE-ограничение, почему письмо строится до коммита. Комментария «получаем список номеров» над функцией получения списка номеров быть не должно. Docstring — у функций с нетривиальным контрактом (что блокирует, что коммитит, что откатывает).
- Осознанные упрощения с известным пределом помечаются комментарием `ponytail:` с условием, когда их чинить. Сейчас такой один: счётчики ограничения частоты в памяти процесса ([security.py](../backend/app/security.py)). Прежнее упрощение «сегодня» по UTC снято: все даты считает [hotel_time.py](../backend/app/hotel_time.py).
- Заготовок на будущее нет: ни закомментированного кода, ни пометок TODO, ни функций, которые никто не вызывает.
- Тексты интерфейса, сообщения об ошибках API и письма — на русском. Идентификаторы, имена файлов, slug и коды (`dates_taken`, `per_stay`) — латиницей.
- Деньги — целые рубли (`int`), без копеек и без `float`. Время для людей — по часам отеля (`hotel_time`), время в базе — `timestamptz`.
- Настройки читаются из `os.getenv` на уровне модуля с значением по умолчанию. Новая настройка добавляется в три места: код, `environment` в [docker-compose.yml](../docker-compose.yml), [.env.example](../.env.example) (и строка в таблицу [07-infrastructure.md](07-infrastructure.md)). Без записи в compose переменная из `.env` в контейнер не попадёт.

## Как добавить поле в номер

1. Колонка в `Room` в [models.py](../backend/app/models.py).
2. Миграция: `docker compose exec backend alembic revision --autogenerate -m "rooms: этаж"`. Для колонки `NOT NULL` в таблице с данными задайте `server_default` в миграции, иначе она не применится к существующим строкам.
3. Поле в `RoomOut` в [schemas.py](../backend/app/schemas.py), иначе оно не попадёт в ответ API. Если поле должен править администратор, добавьте его и в `RoomIn` (сейчас это цена, описание и доступность), и в форму [RoomFormDialog.vue](../frontend/app/components/RoomFormDialog.vue).
4. Значение в словарях номеров в [seed.py](../backend/seed.py), чтобы пустая база наполнялась полностью. Существующие номера сид не перезаписывает, у них поле заполнит миграция или администратор.
5. Поле в интерфейсе `Room` в [types.ts](../frontend/app/types.ts).
6. Вывод в [RoomCard.vue](../frontend/app/components/RoomCard.vue) или на странице номера.
7. `docker compose restart backend`: миграция применится при старте, данные сохранятся.

## Как добавить эндпоинт

Обработчик кладётся в существующий роутер по смыслу ресурса. Новый файл в `routers/` появляется только вместе с новой сущностью, и его нужно подключить в [main.py](../backend/app/main.py).

1. **Доступ.** Публичный — без зависимостей. Для гостя — `user: User = Depends(require_user)`; для брони — `require_verified_user`. Всё под `/api/admin` кладётся в роутер с `dependencies=[Depends(require_admin)]`: тогда закрыть эндпоинт нельзя забыть. Эндпоинт, который по запросу анонима пишет в базу или шлёт письмо, получает ограничители частоты: `dependencies=[Depends(limiter) for limiter in account_limiters]` (или `booking_limiters`, `login_limiters`); новый набор заводится в [security.py](../backend/app/security.py).
2. **Шаблон обработчика:** сессия через `Depends(get_db)`, форма ответа через `response_model`, ошибки как `HTTPException` с русским текстом в `detail`. Ошибки пароля и других полей — через `field_error`, чтобы фронт показал их под полем.
3. **Что отвечать.** Всё, что видно из тела запроса, проверяет Pydantic и отвечает 422; всё, для чего нужна база, проверяет роутер: 400 — запрос неприменим, 404 — нет такого (в том числе **чужого**: бронь, заказ и уборка гостя ищутся с условием владельца, чужая неотличима от несуществующей), 409 — конфликт состояния, 429 — частота или лимит. Правило, которое должно выдерживать гонку запросов, оформляется ограничением базы, а не проверкой в коде.
4. **Транзакция.** Роутер делает `db.commit()` ровно один раз в конце. Действие над объектом берёт его с блокировкой (`get_booking(..., lock=True)`, `with_for_update`), чтобы два параллельных действия шли по очереди.
5. **Брони.** Эндпоинт, который показывает или меняет брони, начинается с `expire_stale_pending(db, background)` (в `GET` сразу `db.commit()`), иначе статусы будут отставать от просрочки. Смена статуса — только через `change_status`.
6. Ответ действия над бронью гостя — `GuestBookingDetail` целиком: фронт обновляет карточку одним ответом.
7. Тест (см. ниже): успех, каждый код ошибки, права (аноним 401, гость 403 для админского).
8. Если фронт использует эндпоинт — тип в [types.ts](../frontend/app/types.ts) и описание в [06-frontend.md](06-frontend.md); строка в таблицу [04-backend.md](04-backend.md).

## Как добавить миграцию

1. Правка моделей в [models.py](../backend/app/models.py).
2. `docker compose exec backend alembic revision --autogenerate --rev-id 0006 -m "кратко, что меняется"`. Существующие миграции нумеруются подряд (`0001` … `0005`), а Alembic по умолчанию даёт случайный идентификатор; `--rev-id` задаёт следующий номер, и файл получает имя `0006_….py`. Проверьте, что `down_revision` указывает на предыдущую (`"0005"`).
3. **Читать сгенерированное.** Autogenerate не видит `CHECK`, `EXCLUDE` и `server_default`-ы, перепутанные порядки не исправляет. Все допустимые значения enum-подобных колонок живут в `CHECK` в миграции (например `bookings_status_check`) и в `StrEnum` в `models.py` одновременно: добавляя значение, правьте оба места.
4. Для `NOT NULL` колонки в непустой таблице: сначала `nullable=True` или `server_default`, затем данные, затем ужесточение. Миграция `0003` удаляет брони, потому что иначе `user_id NOT NULL` не встать, и это допустимо только для учебных данных.
5. Написать `downgrade`, если откат возможен; если теряются данные, сказать об этом комментарием, как в `0003`.
6. `docker compose restart backend` применит миграцию при старте (`alembic upgrade head`). Затем `alembic check`: он сравнивает модели с базой и не должен показать различий.
7. `docker compose exec backend pytest`: тестовая база накатывает те же миграции.

## Как добавить правило авто-решения

Правило — это новая причина ручного разбора или отказа в [booking_rules.py](../backend/app/booking_rules.py).

1. Код причины в `Reason` (`StrEnum`, латиницей, до 32 символов: так задана колонка `reason_codes`).
2. Текст для гостя и администратора в `REASON_TEXTS`. Тест `test_every_reason_has_text` упадёт, если забыть. Для отказа текст должен быть нейтральным и не раскрывать внутренних отметок, как у `client_blocked`.
3. Если правилу нужен факт, которого нет в аргументах `decide`, добавьте **именованный аргумент** и вычислите факт в `submit_booking` ([booking_lifecycle.py](../backend/app/booking_lifecycle.py)). Сам `decide` в базу ходить не должен: тогда он остаётся таблично тестируемым.
4. Условие в `decide` в нужном месте порядка: отказ → причины разбора → подтверждение. Причины разбора **накапливаются**, а не прерывают проверку. Решите, действует ли правило на VIP (`is_vip`).
5. Порог, которым управляет отель, — переменная окружения (по образцу `AUTO_CONFIRM_MAX_NIGHTS`), с записью в compose, `.env.example` и таблицу в [07-infrastructure.md](07-infrastructure.md). Текст причины в `REASON_TEXTS` читает значение порога при импорте.
6. Тесты: строка в параметризации `test_decide_rules` в [test_booking_rules.py](../backend/tests/test_booking_rules.py), проверка с VIP, и один сквозной тест через `POST /api/bookings` в [test_bookings.py](../backend/tests/test_bookings.py).

Фронт править не нужно: причины приходят готовым списком текстов (`reasons`), коды в интерфейсе не используются.

## Как добавить письмо

1. Функция в [mail_templates.py](../backend/app/mail_templates.py), возвращающая `Mail(to, subject, html, text)` из f-строк. Пользовательские значения в HTML проходят `escape`; обе версии, HTML и текстовая, обязательны. Ссылки строятся от `APP_BASE_URL`.
2. **Письмо о переходе брони** — не вызывать `send_mail` вручную: добавьте функцию в `STATUS_MAILS` в [booking_lifecycle.py](../backend/app/booking_lifecycle.py), и `change_status` отправит её при каждом таком переходе, откуда бы он ни пришёл (гость, админ, просрочка, каскад).
3. **Любое другое письмо** — `background.add_task(send_mail, ваше_письмо(...))` в роутере, после того как нужные данные сохранены (`flush`) и до `commit`. Письмо строится сразу, пока сессия открыта и связи брони доступны; в фон уходит готовый объект.
4. Если письмо ссылается на сущность без `id` до сохранения, сделайте `db.flush()` раньше (как делает `change_status`).
5. Тест: `mail.outbox` (бэкенд `memory`) содержит ожидаемое письмо с нужным `to`, темой и ссылкой; при ошибке запроса письма нет.
6. Не отправляйте из функций правил и моделей: письмо ставит только роутер или `change_status`.

## Как добавить услугу

Обычная услуга не требует кода: администратор создаёт её в админке (`POST /api/admin/services`: `slug`, название, описание, категория, цена, единица `per_item`/`per_stay`, порядок, активность). Для стартового каталога добавьте кортеж `(slug, title, description, category, price, unit)` в `SERVICES` в [seed.py](../backend/seed.py): сид добавляет только отсутствующие `slug`, так что существующие услуги и правки администратора он не трогает.

Новая **категория** требует правок в трёх местах: значение в `ServiceCategory` ([models.py](../backend/app/models.py)), миграция, расширяющая `services_category_check`, и подпись в `CATEGORY_LABELS` в [services.ts](../frontend/app/utils/services.ts) (порядок ключей задаёт порядок блоков на странице услуг). Если у категории особые правила времени, как у еды (`ROOM_SERVICE_HOURS`), они добавляются в `check_order_time` в [room_service.py](../backend/app/room_service.py).

Нельзя: удалять услугу с заказами (409, только деактивировать) и менять цену «задним числом»: заказ хранит `unit_price` и `total` снимком.

Подробнее — в [06-frontend.md](06-frontend.md).

Сначала проверьте общие классы в [main.css](../frontend/app/assets/css/main.css). Цвета и отступы берутся из переменных (`var(--accent)`, `var(--space-3)`), а не пишутся числами. Всё специфичное для компонента живёт в его `<style scoped>`.

## Тесты

Запуск: `docker compose exec backend pytest` (сейчас 346 тестов); устройство окружения — в [04-backend.md](04-backend.md). Принципы:

- **Тест на каждое правило и каждый код ошибки.** Новое поведение без теста не принимается; исправление ошибки начинается с теста, который её воспроизводит.
- **Чистые правила — таблицами** без базы (`pytest.mark.parametrize`), как `decide` и `calculate_price`. Остальное — через `TestClient` и фикстуры из [conftest.py](../backend/conftest.py): `client`, `guest_client`, `unverified_client`, `admin_client`, `make_user`, `make_booking`.
- **Исходное состояние готовьте напрямую в базе** (`make_booking` кладёт бронь в любом статусе, минуя `change_status`), а проверяемое действие выполняйте через API.
- **Время** подменяется `monkeypatch.setattr(hotel_time, "hotel_now", ...)`. Поэтому в коде всегда `hotel_time.hotel_today()`, а не `from hotel_time import hotel_today`.
- **Письма** читаются из `mail.outbox`, настройки модулей подменяются `monkeypatch.setattr(модуль, "ИМЯ", значение)`: они прочитаны при импорте.
- Гонки проверяются подготовкой второго конфликтующего состояния (как `test_admin_confirm_race_returns_409_and_keeps_booking_pending`), а не потоками.
- Тесты не зависят друг от друга: каждый идёт в откатываемой транзакции. Не коммитьте мимо сессии `db` и не полагайтесь на данные другого теста.
- Демо-данные в тестах выключены (`SEED_DEMO=false`); тестам сида они нужны, и те создают их фикстурой `demo`.

Имя теста — предложение о поведении: `test_guest_cancel_deadline_boundary`, `test_foreign_booking_is_404`.

## Чего лучше не ломать

| Что | Почему |
|---|---|
| Ограничение `bookings_no_overlap` (EXCLUDE по `room_id` и `daterange`, `WHERE status='confirmed'`) | Единственная гарантия от двойного подтверждения при гонке: проверка в коде эту гонку не выдерживает. Два администратора смогут подтвердить пересекающиеся заявки |
| `TRANSITIONS` и `ORDER_TRANSITIONS` | Единственный источник допустимых переходов и тех, кто их выполняет. Лишний `if status == ...` в роутере разведёт поведение двух мест |
| `change_status` как единственный путь смены статуса брони | Только он пишет журнал `booking_events`, ставит письмо, создаёт и снимает уборки и заказы, отклоняет пересекающиеся заявки. Прямое `booking.status = ...` оставит бронь без письма и без истории |
| Письма ставятся внутри `change_status`, а не в роутерах | Письмо уйдёт для любого источника перехода, включая просрочку и сид. Продублированное письмо в роутере придёт гостю дважды |
| Просрочка и действие в одной транзакции | Если действие упадёт, должны откатиться и статусы, и письма. Не коммитьте просрочку отдельно перед действием |
| Идемпотентность `expire_stale_pending` и `SKIP LOCKED` | Её вызывают все запросы по броням; без блокировки с пропуском параллельные запросы упрутся друг в друга |
| `calculate_price` как единственный расчёт цены | Котировка в форме должна совпадать с суммой брони |
| Снимки цены в брони и заказе | Правка каталога не должна менять уже сделанные брони и заказы |
| Одинаковые ответы `register`, `forgot-password`, `login` для известного и неизвестного email, `DUMMY_PASSWORD_HASH`, пароль проверяется до поиска email | Иначе по ответу и времени можно перебирать зарегистрированные адреса |
| В базе только sha256 токенов (сессии, письма) | Утечка дампа не должна давать рабочих сессий и ссылок |
| Подтверждение email и сброс пароля только `POST` | Почтовые сканеры открывают ссылки `GET`-ом; подтверждение по `GET` сработало бы без человека |
| Условие владельца в запросах кабинета (`owner_id`, `Booking.user_id == user.id`) | Иначе гость увидит или изменит чужую бронь; чужая должна быть неотличима от несуществующей (404) |
| `require_admin` на роутере `/api/admin/*` | Новый эндпоинт админки должен быть закрыт по умолчанию |
| Правило `routeRules` в [nuxt.config.ts](../frontend/nuxt.config.ts) | Без прокси фронт перестанет видеть API, а cookie сессии перестанет доходить до backend |
| Порядок `alembic upgrade head && python seed.py` | Сид упадёт на несуществующих таблицах |
| `-h 127.0.0.1` в healthcheck базы | Backend начнёт стартовать до конца инициализации тома |
| Порты `127.0.0.1:8000` и `127.0.0.1:5432` | API и база станут доступны из сети в обход прокси |
| Идемпотентность сида (по `slug`, по email, «пропускать, если есть») | Каждый старт контейнера запускает сид; он не должен дублировать данные и перезаписывать правки администратора, особенно его пароль |
| Установка окружения в начале [conftest.py](../backend/conftest.py) | Тесты пойдут в рабочую базу вместо `kivana_test` |
| Вызов `hotel_time.hotel_today()` через модуль | Тесты «переводят часы» подменой `hotel_now`; импорт функции по имени подмену обойдёт |

## Вопросы на понимание
