# 06. Frontend

## Nuxt 4 и каталог app

В Nuxt 4 корнем исходников по умолчанию является каталог `app/`. Страницы, компоненты, стили и точка входа лежат в `frontend/app/`, а в корне `frontend/` остаются конфиги, `public/` и манифесты пакетов.

```
frontend/
├── nuxt.config.ts          # прокси /api/**, язык страницы, favicon, опрос файлов
├── tsconfig.json           # ссылки на сгенерированные .nuxt/tsconfig.*.json
├── package.json            # nuxt, vue, vue-router; typescript и @types/node для разработки
├── package-lock.json       # нужен для npm ci в Dockerfile
├── public/
│   ├── favicon.svg
│   └── images/rooms/       # шесть SVG-плейсхолдеров
└── app/
    ├── app.vue             # AppHeader + NuxtPage + AppFooter
    ├── error.vue           # страница ошибки 404 и 5xx
    ├── types.ts            # интерфейсы ответов API
    ├── assets/css/main.css # переменные и общие классы
    ├── components/
    │   ├── AppHeader.vue
    │   ├── AppFooter.vue
    │   ├── RoomCard.vue
    │   └── BookingForm.vue
    └── pages/
        ├── index.vue
        ├── contacts.vue
        ├── rooms/
        │   ├── index.vue
        │   └── [slug].vue
        └── admin/
            ├── index.vue   # список заявок
            └── login.vue   # вход
```

Каталогов `layouts/`, `stores/`, `plugins/`, `middleware/` и `composables/` нет. Макет один и живёт в [app.vue](../frontend/app/app.vue). Проверка входа в админку сделана прямо на странице, отдельный middleware ради одной страницы не нужен.

## Роутинг

Файловый: `pages/index.vue` даёт `/`, `pages/rooms/[slug].vue` даёт `/rooms/:slug`, `pages/admin/index.vue` даёт `/admin`. Ссылки на админку в навигации нет, администратор открывает адрес сам. Страницы админки помечены `robots: noindex`.

## Работа с данными

Данные страниц загружаются через `useFetch` по относительному пути, действия пользователя отправляются через `$fetch`. `useFetch` кэширует результат и передаёт его из SSR в браузер для гидратации, а для разового нажатия кнопки это не нужно.

```ts
const { data: hotel } = await useFetch<Hotel>('/api/hotel', { key: 'hotel' })
```

Общий ключ `hotel` у подвала, главной и контактов заставляет Nuxt выполнить один запрос на рендер вместо трёх.

**Ошибки загрузки.** `useFetch` не бросает исключение, а заполняет `error`. Каждая страница проверяет его явно и показывает своё сообщение: «Не удалось загрузить номера» вместо ложного «Ничего не найдено». Карточка номера различает причины: 404 от API превращается в страницу «Такой страницы нет», любая другая ошибка — в 503.

**Страница ошибки.** [error.vue](../frontend/app/error.vue) заменяет весь `app.vue`, когда страница бросила фатальную ошибку, поэтому шапку и подвал она подключает сама. Тексты на русском, кнопка ведёт в каталог через `clearError`.

Типы ответов описаны в [types.ts](../frontend/app/types.ts). Корневой [tsconfig.json](../frontend/tsconfig.json) устроен так, как рекомендует Nuxt 4: он ссылается на четыре конфига, которые Nuxt генерирует в `.nuxt/` для кода приложения, сервера, общего кода и самого `nuxt.config.ts`. Пакет `@types/node` нужен последнему: конфиг читает `process.env`. Тип `any` в проекте не встречается. Разбор ошибок `$fetch` сужает неизвестное значение до `{ data?: { detail?: unknown } }` и проверяет тип перед использованием.

## Форма заявки

[BookingForm.vue](../frontend/app/components/BookingForm.vue) держит четыре флага: `errors` для подписей под полями, `serverError` для плашки с ответом сервера, `isSent` для замены формы подтверждением и `isSending` для блокировки кнопки на время запроса.

Клиентская проверка повторяет серверную: имя, от 10 до 15 цифр в телефоне, формат почты, дата заезда не в прошлом, выезд позже заезда, число гостей не больше вместимости. Поля ограничены по длине атрибутом `maxlength` с теми же пределами, что на сервере.

Ответ сервера разбирает функция `errorMessage`. Строковый `detail` из ответов 400, 404, 409 и 429 показывается как есть, он уже на русском. Ответ 422 приходит списком ошибок, и на русском в нём только сообщения собственных валидаторов с префиксом `Value error, `. Их форма показывает без префикса, а на остальные выводит общее сообщение.

## Админка

**Вход** — [pages/admin/login.vue](../frontend/app/pages/admin/login.vue). Форма отправляет логин и пароль на `/api/admin/login`. Backend ставит httpOnly cookie, и страница переходит на `/admin`. Сам токен JavaScript не видит.

**Список заявок** — [pages/admin/index.vue](../frontend/app/pages/admin/index.vue). Логика страницы:

1. `useFetch` загружает `/api/admin/bookings` с реактивным `query`: фильтр статуса, `limit` и `offset`. При SSR Nuxt пересылает cookie входящего запроса, поэтому таблица приходит уже отрисованной.
2. Если API ответил 401, страница перенаправляет на вход. Для запроса без cookie это происходит ещё на сервере, и браузер получает 302.
3. Кнопки «Подтвердить» и «Отменить» отправляют PATCH и перезагружают список. Ответ 409 показывается плашкой, ответ 401 возвращает на вход.
4. Смена фильтра сбрасывает страницу на первую, иначе можно оказаться на пустой пятой странице короткого списка.

Время создания заявки форматируется с явным часовым поясом `Europe/Moscow`. Без него сервер в UTC и браузер в Москве отрисовали бы разное время, и гидратация разошлась бы. Даты заезда и выезда форматируются разбором строки, без `Date`: `new Date('2026-10-10')` — это полночь по UTC, и западнее Гринвича такая дата показалась бы предыдущим днём.

## Стили

[main.css](../frontend/app/assets/css/main.css) объявляет палитру, отступы, радиусы и тень в CSS-переменных, а также общие классы: `.container`, `.section`, `.grid`, `.card`, `.button`, `.field`, `.notice`, `.tag`. Остальное живёт в `<style scoped>` компонентов. Таблица админки на узком экране прокручивается внутри карточки, страница целиком вбок не уезжает.
