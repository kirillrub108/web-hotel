# 06. Frontend

## 1. Nuxt 4 и каталог app

В Nuxt 4 корнем исходников по умолчанию является каталог `app/`. Страницы, компоненты, стили и точка входа лежат в `frontend/app/`, а в корне `frontend/` остаются конфиги, `public/` и манифесты пакетов. Рендеринг — SSR (режим Nuxt по умолчанию): первую страницу собирает сервер, дальше работает клиентская навигация.

```
frontend/
├── nuxt.config.ts          # прокси /api/**, viewport-fit=cover, passwordMinLength, опрос файлов
├── tsconfig.json           # ссылки на сгенерированные .nuxt/tsconfig.*.json
├── package.json            # nuxt, vue, vue-router; typescript и @types/node для разработки
├── public/                 # favicon.svg и шесть SVG-плейсхолдеров номеров
└── app/
    ├── app.vue             # загрузка текущего пользователя + AppHeader + NuxtPage + AppFooter; липкий подвал
    ├── error.vue           # страница ошибки 404 и 5xx
    ├── types.ts            # интерфейсы ответов и тел запросов API
    ├── assets/css/main.css # переменные, адаптивность, общие классы
    ├── middleware/auth.global.ts   # доступ к /account/** и /admin/**
    ├── composables/useCurrentUser.ts
    ├── utils/              # apiError.ts, booking.ts, promo.ts, services.ts
    ├── components/         # шапка, подвал, формы, диалоги, бейджи, таймлайн
    └── pages/              # маршруты, см. раздел 2
```

Каталогов `layouts/`, `stores/` и `plugins/` нет: макет один и живёт в [app.vue](../frontend/app/app.vue), состояние — один `useState` в [useCurrentUser.ts](../frontend/app/composables/useCurrentUser.ts). Pinia не нужна, пока общего состояния ровно одно.

Нестандартное в [nuxt.config.ts](../frontend/nuxt.config.ts):

| Настройка | Зачем |
|---|---|
| `routeRules['/api/**'].proxy` на `API_BASE` | Один относительный путь работает и в браузере, и при SSR; CORS в FastAPI не нужен, cookie ставится на домен сайта |
| `viewport` с `viewport-fit=cover` | Включает `env(safe-area-inset-*)` для вырезов и «островков», без него `--safe-*` всегда 0 |
| `runtimeConfig.public.passwordMinLength` = 15 | Подсказка в [PasswordField.vue](../frontend/app/components/PasswordField.vue); в compose переопределяется `NUXT_PUBLIC_PASSWORD_MIN_LENGTH` из `PASSWORD_MIN_LENGTH` backend |
| `WATCH_POLLING` | Опрос файлов нужен для bind-mount с Windows, где нет событий inotify |
| `htmlAttrs.lang = 'ru'`, favicon, description | Язык страницы и мета-описание |

## 2. Маршруты и доступ по ролям

Роутинг файловый. Три уровня доступа:

| Уровень | Маршруты | Страницы |
|---|---|---|
| Публичные | `/`, `/rooms`, `/rooms/:slug`, `/services`, `/contacts`, `/privacy` | Главная, каталог с фильтрами, карточка номера с бронированием, каталог услуг, контакты, согласие на обработку данных |
| Аккаунт (вход не нужен) | `/login`, `/register`, `/forgot-password`, `/reset-password?token=`, `/verify-email?token=` | Токены из писем подтверждаются кнопкой, а не при открытии страницы: почтовые сканеры заранее переходят по ссылкам |
| Кабинет (нужен вход) | `/account`, `/account/bookings`, `/account/bookings/:id`, `/account/profile` | Обзор, список броней, бронь с историей, заказами услуг и выбором времени уборки, профиль и смена пароля |
| Админка (роль `admin`) | `/admin`, `/admin/clients`, `/admin/clients/:id`, `/admin/rooms`, `/admin/promos`, `/admin/services`, `/admin/service-orders`, `/admin/housekeeping` | Заявки, клиенты и CRM, номера, акции, каталог услуг, заказы услуг, расписание уборок |

**Middleware.** [auth.global.ts](../frontend/app/middleware/auth.global.ts) срабатывает на каждой навигации, но проверяет только пути `/account` и `/admin` (и вложенные):

1. Ждёт `useCurrentUser().load()`.
2. Гость → `/login?next=<полный путь>`.
3. Вошедший не администратор на `/admin/**` → `/account`.

Проверка идёт до отрисовки, поэтому при SSR браузер получает 302 без мигания страницы. Это удобство, а не защита: данные всё равно отдаёт backend, где `require_admin` и `require_verified_user` проверяют роль заново. Поэтому страницы админки дополнительно обрабатывают 401 от API (сессия истекла, пока страница открыта) функцией `toLogin`: очищает состояние и ведёт на `/login?next=…`. Страница входа пропускает `next` только если он начинается с `/` и не с `//`, иначе получился бы открытый редирект ([login.vue](../frontend/app/pages/login.vue)).

Ссылки в шапке зависят от роли: [AppHeader.vue](../frontend/app/components/AppHeader.vue) показывает «Админку» только при `user.role === 'admin'`, «Кабинет» — вошедшему, «Войти» — гостю. Страницы кабинета и админки помечены `robots: noindex`.

## 3. Состояние и данные

**Текущий пользователь.** [useCurrentUser.ts](../frontend/app/composables/useCurrentUser.ts) — `useState('current-user')` плюс `load()`, `refresh()`, `clear()`. `load()` обёрнут в `callOnce`, поэтому `/api/auth/me` вызывается один раз на открытие сайта: при SSR на сервере, результат уезжает в браузер вместе со страницей. Запрос идёт через `useRequestFetch`, он пробрасывает cookie браузера на сервер — иначе при SSR гость всегда выглядел бы невошедшим. Любая ошибка `/me` (401 или недоступный API) превращается в `null`: сайт показывается как для гостя. Токен сессии лежит в httpOnly-cookie, JavaScript его не видит.

**Загрузка.** Данные страниц — через `useFetch` по относительному пути, действия пользователя — через `$fetch`. `useFetch` кэширует результат и передаёт его из SSR в браузер, для разового нажатия кнопки это лишнее. Общий ключ `hotel` у подвала, главной и контактов даёт один запрос на рендер вместо трёх; так же работает ключ `services`.

**Ошибки.** `useFetch` не бросает исключение, а заполняет `error`, поэтому каждая страница проверяет его сама и показывает своё сообщение («Не удалось загрузить заявки»), а не ложное «ничего не найдено». Карточки номера и брони различают причины: 404 превращается в страницу «Такой страницы нет», остальное — в 503. [error.vue](../frontend/app/error.vue) заменяет весь `app.vue`, поэтому шапку и подвал подключает сама.

**Разбор ответов API.** [apiError.ts](../frontend/app/utils/apiError.ts): `apiErrorMessage` берёт строковый `detail` как есть (он уже на русском) либо первое русское сообщение из ответа 422 без префикса `Value error, `; встроенные английские сообщения Pydantic заменяются запасным текстом. `apiFieldErrors` раскладывает 422 по полям для подписей под инпутами.

**Словари и форматирование.** Подписи статусов, сегментов, категорий и слотов живут только в [booking.ts](../frontend/app/utils/booking.ts) и [services.ts](../frontend/app/utils/services.ts): бейджи, формы и админка берут их оттуда. Часовой пояс задан явно (`Europe/Moscow`, совпадает с `HOTEL_TZ` backend): без него сервер в UTC и браузер в Москве показали бы разное время, и гидратация разошлась бы. Дату `YYYY-MM-DD` форматирует разбор строки, не `Date`: `new Date('2026-10-10')` — полночь UTC, и западнее Гринвича показалась бы предыдущим днём.

Типы — в [types.ts](../frontend/app/types.ts). Корневой [tsconfig.json](../frontend/tsconfig.json) ссылается на четыре конфига, которые Nuxt генерирует в `.nuxt/`. Тип `any` в коде не встречается; ошибки `$fetch` сужаются из `unknown` явно.

## 5. Адаптивная вёрстка

Весь код адаптивности — в [main.css](../frontend/app/assets/css/main.css) и в `<style scoped>` компонентов. Поддерживаются телефон от 360 px, планшет и десктоп; горизонтальной прокрутки страницы нет нигде.

### 5.1. Брейкпоинты и принцип

| Диапазон | Что считается |
|---|---|
| < 640 px | Телефон |
| 640–1023 px | Планшет |
| ≥ 1024 px | Десктоп |

Дополнительно только одна «ступенька»: 1024–1279 px (уплотнение таблиц, см. 5.5).

**Структура написана mobile-first**: база — мобильная, `min-width: 640px` и `1024px` её раскрывают (контейнер, сетки, шапка, диалог, `.facts`). **Таблицы-карточки и размеры тач-целей сделаны наоборот**: одним блоком под `max-width: 1023.98px` и `@media (min-width: 1024px) and (pointer: fine)`. Так задумано ради неизменности десктопа: всё, что превращает таблицу в карточки или увеличивает кнопки, лежит в одном месте и не может случайно задеть вид на 1280 px. Значения `.98` в `max-width` исключают двойное срабатывание на границе с `min-width` (при дробном zoom).

### 5.2. Контейнер и вырезы экрана

`.container` — `max-width: var(--container)` (1120px) и боковой отступ `max(16px, var(--safe-*))` на телефоне, `max(24px, var(--safe-*))` от 640. Переменные `--safe-top|right|bottom|left` — это `env(safe-area-inset-*, 0px)`; работают благодаря `viewport-fit=cover` в [nuxt.config.ts](../frontend/nuxt.config.ts). Их используют шапка (`padding-top`), подвал (`padding-bottom`), липкая кнопка брони, панель кнопок диалога и лента `.subnav--scroll`. Остальные токены: `--tap: 44px`, `--space-1..5` (8–64px), `--radius`, `--radius-sm`.

### 5.3. Шапка с бургером

[AppHeader.vue](../frontend/app/components/AppHeader.vue). Липкая (`position: sticky`, `z-index: 10`, учитывает `--safe-top`).

- **< 640**: пункты прячутся (`display: none`), кнопка-бургер 44×44 раскрывает их вертикальным списком под шапкой (`.header__nav--open`). Список ограничен по высоте `100dvh − safe-top − 64px` и прокручивается сам.
- **Доступность**: у кнопки `aria-controls="site-nav"`, `aria-expanded`, `aria-label="Меню"`; `Esc` на шапке закрывает меню (`@keydown.esc`); клик по любому пункту тоже закрывает.
- **≥ 640**: кнопка скрыта, пункты в строку, зазор 16px, с 1024 — 24px.
- **Пункты по роли**: все — «Главная», «Номера», «Услуги», «Контакты»; гость — «Войти»; вошедший — «Кабинет»; администратор — ещё «Админка».
- Только на `≥1024 && pointer: fine` у шапки возвращаются прежние компактные отступы (`min-height: 0`).

### 5.4. Подменю `.subnav`

Таблетки разделов кабинета ([AccountNav.vue](../frontend/app/components/AccountNav.vue): «Обзор», «Мои брони», «Профиль», для админа ещё «Админка») и админки ([AdminNav.vue](../frontend/app/components/AdminNav.vue): семь разделов). На десктопе с мышью `.subnav` превращается в обычные текстовые ссылки с зазором 24px.

На телефоне админка получает `.subnav--scroll`: однострочная лента без переноса, с горизонтальной прокруткой и скрытым скроллбаром; отрицательные боковые margin и такой же padding делают ленту во всю ширину экрана. Семь пунктов в строку не помещаются, поэтому `AdminNav` в `onMounted` вызывает `scrollIntoView({ inline: 'center', block: 'nearest' })` для `.subnav__link--active`: активный раздел виден сразу, иначе на «Уборке» активной была бы невидимая справа вкладка. Подсветка раздела считается по префиксу пути: карточка клиента подсвечивает «Клиенты».

### 5.5. Таблицы админки: строки превращаются в карточки

Все таблицы админки — `.data-table` внутри `.card.table-wrap`. На **≥ 1024** это обычная таблица. На **< 1024**:

- `thead` скрыт визуально (clip-приём `position: absolute; clip: rect(0 0 0 0)`), но остаётся в DOM для экранных дикторов;
- `table`, `tbody`, `tr`, `td` получают `display: block`; строка — карточка с отступами и нижней линией;
- подпись поля берётся из атрибута: `td[data-label]::before { content: attr(data-label) }`. Поэтому **каждая `<td>` с данными обязана иметь `data-label`**, равный тексту её `<th>`;
- `td.nowrap` теряет `white-space: nowrap`; ссылки в ячейках без `data-label` получают `min-height: 44px`;
- **640–1023**: `tr` — сетка из двух столбцов полей; `td.actions`, `td.reasons`, `td.description` и `td[colspan]` занимают всю ширину (`grid-column: 1 / -1`). Строка истории заявки (`<td colspan="7">` с таймлайном) тоже идёт на всю ширину;
- **1024–1279**: отступы ячеек уменьшены с 14 до 8 px по горизонтали, иначе самая широкая таблица, «Заявки» (семь столбцов), не помещается без прокрутки.

**Ячейка `.actions`.** На десктопе она остаётся настоящей `td` (`display: table-cell`), а кнопки внутри идут столбиком (`> * { display: flex; width: 100% }`). Делать саму ячейку flex-контейнером нельзя: она выпала бы из табличной раскладки, и линия под строкой оборвалась бы в её месте. На < 1024 ячейка становится flex-контейнером с переносом, кнопки тянутся (`flex: 1 1 auto`), сверху разделитель; `.link-button` в ней рисуется рамкой, как кнопка; `.hint` занимает всю строку.

**Как добавить таблицу:**

1. Обёртка `<div class="card table-wrap"><table class="data-table">`.
2. В `<thead>` — заголовки столбцов. Столбец с кнопками оставьте с пустым `<th />`.
3. В каждой `<td>` с данными — `data-label="…"`, совпадающий с заголовком столбца.
4. Ячейку с кнопками пометьте `class="actions"` и не давайте ей `data-label`. Кнопки кладите прямыми потомками: `.button--small`, `.link-button`.
5. Короткие значения (даты, суммы) — `class="nowrap"`; длинный текст — `class="description"` или `reasons`, чтобы на планшете он шёл на всю ширину.
6. Строка-расширение — `<td colspan="N">` без `data-label`.
7. Проверьте на 360, 768, 1024 и 1280 px (раздел 5.9).

Образцы: [admin/index.vue](../frontend/app/pages/admin/index.vue) (заявки, самая сложная), [admin/rooms/index.vue](../frontend/app/pages/admin/rooms/index.vue) (колонка `description`), [admin/clients/index.vue](../frontend/app/pages/admin/clients/index.vue).

Цена решения: `display: block` у `table/tr/td` на < 1024 снимает табличную семантику у части экранных дикторов (строки и ячейки перестают объявляться как таковые). При необходимости на этих элементах добавляют `role="table|row|cell"`, см. [09-tech-debt.md](09-tech-debt.md).

### 5.6. Формы и тач-цели

- Одна колонка на телефоне; от 640 пары полей (`.booking__row`: заезд и выезд) встают в два столбца.
- `.field input|select|textarea` наследуют шрифт страницы (`font: inherit`, 17px): поля не меньше 16px, и iOS не увеличивает страницу при фокусе. `min-height: var(--tap)` = 44px.
- Нативные типы вместо самодельных масок: `type="email"` + `inputmode="email"` (вход, регистрация, восстановление), `type="tel"` + `inputmode="tel"` (телефон в брони и профиле), `type="date"` (даты брони, акций, фильтры админки), `type="datetime-local"` (время заказа услуги), `type="number"` + `inputmode="numeric"` (гости, цены, количество), `type="search"` + `enterkeyhint="search"` (поиск клиентов). Мобильные браузеры сами показывают нужную клавиатуру и календарь; проверка формата остаётся на сервере.
- `.button`, `.link-button`, `.tabs__item`, `.checkbox` (чекбокс 22px в зоне 44px) и пункты `.subnav` — не ниже 44px. Только на `≥1024 && pointer: fine` компактные размеры возвращаются (`.button--small`, `.tabs__item`, `.link-button`, чекбоксы), то есть мышь на десктопе видит прежний вид, а планшет с тачем — крупные цели.
- Вторичный текст меньше 16px сознательно: подписи полей 0.9rem, подсказки 0.85rem, подпись карточки `data-label` 0.78rem. Автозум iOS срабатывает только на полях ввода, а они ≥ 16px.

### 5.7. Модальные окна

Нативный `<dialog>` с классом `.dialog`; компонент монтируется по `v-if` и вызывает `showModal()` в `onMounted`. Нативный `showModal` даёт фокус-ловушку и `Esc` бесплатно, `@close` возвращает управление родителю.

- **< 640**: «шторка» снизу во всю ширину (`margin: auto 0 0`, скругление только сверху, `max-height: 92dvh`), панель `.dialog__actions` липкая (`position: sticky; bottom: 0`) с отступом `max(24px, var(--safe-bottom))`; кнопки делят ширину поровну. Липкая панель нужна, чтобы «Подтвердить» не уезжала за экран при открытой клавиатуре и длинной форме.
- **≥ 640**: окно по центру шириной `min(520px, 100vw − 32px)`, кнопки справа, панель обычная.
- **Блокировка прокрутки страницы**: `body:has(dialog[open]) { overflow: hidden }`, без JavaScript.

### 5.8. Остальные приёмы

**Липкая кнопка «Забронировать»** — блок `.cta` в [rooms/[slug].vue](../frontend/app/pages/rooms/[slug].vue). `position: fixed` у нижней кромки с учётом `--safe-bottom`; показывает цену за ночь и ссылку `href="#booking"` на блок формы (`scroll-margin-top: 80px` — высота липкой шапки). Только < 1024 (`display: none` с десктопа, там форма сама липкая `position: sticky; top: 90px`). Кнопка видна только пока форма брони и подвал вне экрана: два `IntersectionObserver` в `onMounted` следят за `<aside id="booking">` и `<footer>`. Скрывается она сдвигом и `visibility: hidden`, чтобы невидимая кнопка не получала фокус; при `prefers-reduced-motion` анимации нет. Для снятого с продажи номера она не показывается никогда (`room.is_available`).

**Липкий подвал.** `#__nuxt` — flex-колонка с `min-height: 100dvh`, `main` — `flex: 1 0 auto`. На коротких страницах (вход, пустой список) подвал прижат к низу экрана, а не плавает посреди белого поля.

**`.facts`** — список «название — значение» на `<dl>`. На телефоне друг под другом, от 640 в две колонки (`fit-content(14rem) 1fr`); `dd` с `overflow-wrap: anywhere`, чтобы длинный email не распирал страницу. Применяется на странице брони и в карточке клиента.

**Таймлайн** — `.timeline` в [BookingTimeline.vue](../frontend/app/components/BookingTimeline.vue): линия `border-left` и точка в `::before`; своих брейкпоинтов нет, он тянется по ширине родителя.

**Подвал и ссылки.** До 1024 ссылки подвала получают `padding: 10px 0` для тач-зоны.

### 5.9. Как проверять вёрстку

Автотестов вёрстки нет, проверка ручная. Чек-лист на каждый затронутый экран:

1. Ширины 360, 768, 1024 и 1280 px (минимум 360/768/1280).
2. Горизонтального прокручивания страницы нет (`document.documentElement.scrollWidth <= innerWidth`).
3. Видимые интерактивные элементы не меньше 44×44 на тач-ширинах.
4. Поля ввода не меньше 16px; у полей правильные `type` и `inputmode`.
5. Таблица: у каждой `td` есть `data-label`, `.actions` не ломает строку.
6. Диалог: на 360 панель кнопок видна без прокрутки страницы, фон не прокручивается.
7. Страница номера: кнопка «Забронировать» появляется, а над формой и над подвалом исчезает.
8. Под ролями администратора и гостя.

**Что было сделано при выпуске адаптивной версии.** Playwright делал скриншоты всех страниц на 360, 768 и 1280 px под ролями `admin` и `guest` и считал метрики: горизонтальное переполнение, число тач-целей меньше 44px, число полей со шрифтом меньше 16px, соответствие `type` и `inputmode`. Результат: переполнения нет ни на одной странице; тач-цели и шрифты в норме на 360 и 768. Скриншоты десктопа 1280 сверены с версией до правок: ухудшений нет; улучшены линии строк таблиц у `.actions` и липкий подвал на коротких страницах. Скрипты проверки в репозиторий не вошли (см. [09-tech-debt.md](09-tech-debt.md)).
