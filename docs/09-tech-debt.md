# 09. Слабые места и техдолг

Раздел писался без щажения кода. Часть пунктов — сознательные ограничения учебного проекта, часть — то, что сломается при первой же попытке использовать код всерьёз. Отличать одно от другого важно, поэтому у каждого пункта указан статус.

## Функциональные дыры

**Занятость дат не проверяется.** *Сознательное ограничение.* Две заявки на один и тот же номер на одни и те же даты создадутся обе, и никто об этом не узнает. В [bookings.py](../backend/app/routers/bookings.py) нет ни одного запроса к существующим заявкам. Это следствие решения «заявка, а не бронь»: подтверждает даты администратор вручную. Как только появится настоящее бронирование, здесь понадобится проверка пересечения интервалов и блокировка строки номера на время транзакции.

**Заявки некуда посмотреть.** *Сознательное ограничение.* Данные попадают в `bookings` и не читаются ни одним эндпоинтом. Единственный способ их увидеть — `psql`. Админки в проекте нет по условию задачи.

**Даты в прошлом принимаются.** *Долг.* Поле `min` в форме мешает выбрать вчерашний день мышью, но curl примет заявку на 2020 год: в `BookingCreate` сравниваются только `check_in` и `check_out` между собой. Правило «заезд не раньше сегодня» относится к телу запроса и должно жить в Pydantic.

**Отправка заявки ничем не ограничена.** *Долг.* Эндпоинт открыт, аутентификации нет, ограничения частоты нет. Скрипт может залить в таблицу произвольное количество строк. Для публичного развёртывания нужен как минимум лимит по адресу.

## Данные и схема

**Миграций нет.** *Сознательное ограничение с известной ценой.* `Base.metadata.create_all` в [seed.py](../backend/seed.py) создаёт только отсутствующие таблицы и не трогает существующие. Любое изменение колонки требует `docker compose down -v`, то есть потери данных. Для учебного проекта это дешевле Alembic, для чего-либо ещё — нет.

**Нет индекса на `bookings.room_id`.** *Долг, пока незаметный.* Внешний ключ индекс не создаёт. На десятке строк это не видно; на выборках заявок по номеру появится последовательное сканирование.

**Удобства в JSON.** *Сознательное ограничение.* Искать и фильтровать по ним нельзя, опечатка в названии ничем не ловится. См. [05-data-model.md](05-data-model.md).

**Валидация почты регулярным выражением.** *Сознательное ограничение.* Выражение в [schemas.py](../backend/app/schemas.py) отсеивает грубые ошибки и пропускает многое из того, что не является рабочим адресом. Полноценная проверка стоила бы отдельной зависимости.

## Тесты

**Тесты работают с рабочей базой и зависят от данных сида.** *Долг.* [test_api.py](../backend/tests/test_api.py) ожидает ровно шесть номеров и наличие slug `lyuks`. Добавление седьмого номера в сид уронит тест, не связанный с изменением. На пустой базе упадут четыре теста из семи. Отдельная тестовая база не поднималась по условию задачи, но это именно компромисс, а не хорошая практика.

**Успешное создание заявки не покрыто тестом.** *Долг.* Тест проверяет только отказ с кодом 422. Тест на успешный путь оставлял бы за собой строку в общей базе — прямое следствие предыдущего пункта.

## Инфраструктура

**Оба контейнера работают в режиме разработки.** *Сознательное ограничение.* Uvicorn с автоперезапуском и Nuxt dev-сервером удобны для чтения и правки кода, но медленнее и тяжелее собранной версии. Продакшен-конфигурации в проекте нет.

**Пароль базы лежит в compose и равен `hotel`.** *Сознательное ограничение.* Порт 5432 при этом открыт наружу. Для локальной машины приемлемо, для чего угодно за её пределами — нет.

**Опрос файлов включён безусловно.** *Долг.* Настройка `usePolling` в [nuxt.config.ts](../frontend/nuxt.config.ts) нужна из-за bind-mount на Windows, который не отдаёт события inotify. На Linux и macOS она просто тратит процессорное время. Правильнее было бы включать её переменной окружения.

**Падение backend роняет страницы.** *Долг.* Если backend недоступен, `useFetch` при серверном рендере бросает исключение, и Nuxt отдаёт 500 вместо страницы с сообщением. Обработки этого случая на страницах нет.

## Расхождения между кодом и документацией

На момент генерации расхождений не обнаружено: README и `docs/` написаны по текущему состоянию кода. Одно место требует внимания при чтении: в исходном техническом задании путь к стилям указан как `assets/css/main.css`, тогда как в Nuxt 4 корнем исходников является `app/`, и фактический путь — [frontend/app/assets/css/main.css](../frontend/app/assets/css/main.css). Файл ровно один, отличается только префикс.

Файла `LICENSE` в репозитории нет, поэтому условия распространения не определены. В README на этом месте стоит пометка.
