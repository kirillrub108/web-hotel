Файлов `__init__.py` нет: namespace-пакеты Python 3.3+ разрешают `from app.routers import rooms` без них. Alembic добавляет каталог `backend/` в путь импорта сам, через `prepend_sys_path` в [alembic.ini](../backend/alembic.ini).

## Слои

```
роутер (routers/*.py)      HTTP: путь, доступ, коды ответов, commit
   │
   ├── schemas.py          проверка тела и параметров (422)
   ├── booking_lifecycle   переходы статусов, письма, просрочка
   │      ├── booking_rules   чистые правила, без БД
   │      ├── housekeeping, room_service   каскады на уборки и заказы
   │      └── mail_templates → mail
   └── promos, crm         запросы с показателями
          │
        models.py → PostgreSQL
```

Принцип: роутер отвечает за HTTP и транзакцию, правила живут в модулях рядом. [booking_rules.py](../backend/app/booking_rules.py) не ходит в базу: все факты приходят аргументами, поэтому цена и авто-решение проверяются табличными тестами без БД. Факты из базы собирает вызывающий код ([submit_booking](../backend/app/booking_lifecycle.py), [promos.py](../backend/app/promos.py)).

Функции модулей **не вызывают `commit`**: транзакцией владеет роутер. Поэтому просрочка, переход статуса, каскад на уборки и постановка писем либо сохраняются вместе, либо не сохраняются вовсе.

## Подключение к базе

[database.py](../backend/app/database.py) держит четыре вещи: `DATABASE_URL` из окружения с дефолтом `postgresql+psycopg://kivana:kivana@localhost:5432/kivana`, `engine` с `pool_pre_ping=True`, фабрику сессий (`autoflush=False`) и декларативную базу. Зависимость `get_db` — генератор с `try/finally`, который всегда закрывает сессию.

`pool_pre_ping` проверяет соединение перед выдачей из пула. Без него первый запрос после долгой паузы падал бы, если база успела закрыть простаивающее соединение. `autoflush=False` — сброс в базу происходит только там, где код его вызывает явно (`db.flush()` в `change_status`), поэтому момент срабатывания ограничений предсказуем.

## Доступ

Администратор — обычный пользователь с `role='admin'`, а не отдельная сущность с паролем из окружения. Всё держится на одной сессии и четырёх зависимостях из [sessions.py](../backend/app/sessions.py):

| Зависимость | Что делает | Ответ при отказе |
|---|---|---|
| `get_current_user` | Читает cookie `kivana_session`, ищет по sha256 токена живую сессию активного пользователя; без cookie возвращает `None` | — |
| `require_user` | Нужен вход | 401 «Требуется вход» |
| `require_verified_user` | Вход и подтверждённый email | 403 «Подтвердите email, чтобы бронировать номера» |
| `require_admin` | Вход и `role='admin'` | 403 «Доступ только для администратора» |

Все роутеры `/api/admin/*` получают `dependencies=[Depends(require_admin)]` на уровне `APIRouter`, поэтому новый эндпоинт админки закрыт автоматически. Подтверждённый email требуется только для `POST /api/bookings`: кабинет, заказы услуг и уборки доступны после входа.

**Сессия.** При входе создаётся случайный токен (`secrets.token_urlsafe(32)`), в cookie `kivana_session` уходит он сам, а в таблицу `sessions` — только его sha256. Утечка дампа базы не даёт готовых сессий. Cookie `httponly`, `samesite=lax`, `secure` включается `COOKIE_SECURE=true`. Срок жизни: гость 14 дней (`SESSION_TTL_GUEST_DAYS`), администратор 12 часов (`SESSION_TTL_ADMIN_HOURS`). Сессии на нескольких устройствах живут независимо; смена пароля удаляет все, кроме текущей, сброс пароля — все. Планировщика нет, поэтому истёкшие сессии пользователя удаляются при его следующем входе.

Серверное хранение вместо подписанной cookie даёт то, чего у прежнего HMAC-токена не было: принудительный выход (удаление строк) и отзыв доступа при блокировке (`is_active=false` отсекает сессию в `get_current_user`).

**CSRF.** Отдельной защиты нет, её даёт `samesite=lax`: браузер не отправит cookie с POST/PATCH/DELETE, пришедшим с чужого сайта. Подтверждение email и сброс пароля, наоборот, сделаны только POST по кнопке на странице: почтовые сканеры заранее открывают ссылки из писем GET-запросом, и подтверждение по GET срабатывало бы без человека.

## Эндпоинты

Префикс задаётся у каждого роутера, поэтому путь виден в том же файле, где написан обработчик. Столбец «Доступ»: **публично**, **вход** (`require_user`), **вход + email** (`require_verified_user`), **admin**. Для admin всегда добавляются 401 и 403, для «вход» — 401; в столбце «Ошибки» они не повторяются.

### Публичные

| Метод | Путь | Файл | Успех | Ошибки |
|---|---|---|---|---|
| GET | `/api/health` | [main.py](../backend/app/main.py) | 200 | — |
| GET | `/api/hotel` | [hotel.py](../backend/app/routers/hotel.py) | 200 | 404, если база пуста |
| GET | `/api/rooms` | [rooms.py](../backend/app/routers/rooms.py) | 200, фильтры `capacity`, `max_price`; возможен пустой список | 422 |
| GET | `/api/rooms/{slug}` | rooms.py | 200 | 404 |
| GET | `/api/rooms/{slug}/quote` | rooms.py | 200: свободен ли номер, цена, скидка | 400 (промокод не подошёл), 404, 422 |
| GET | `/api/services` | [services.py](../backend/app/routers/services.py) | 200, только активные услуги | — |

`quote` вызывает те же `calculate_price` и `find_promo`, что и создание брони, поэтому сумма в форме совпадает с суммой в брони. Вход необязателен (`get_current_user`): с сессией применяются персональные промокоды, без неё персональный код отклоняется.

### Аккаунт: `/api/auth`

| Метод | Путь | Доступ | Успех | Ошибки |
|---|---|---|---|---|
| POST | `/register` | публично, лимит `account` | 204 | 422, 429 |
| POST | `/login` | публично, лимит `login` | 200 + cookie | 401, 422, 429 |
| POST | `/logout` | публично | 204, cookie удаляется | — |
| GET | `/me` | вход | 200 | — |
| POST | `/verify-email` | публично | 204 | 400 (токен неверен, использован, истёк), 422 |
| POST | `/resend-verification` | вход, лимит `account` | 204 | 400 (уже подтверждён), 429 |
| POST | `/forgot-password` | публично, лимит `account` | 204 всегда | 422, 429 |
| POST | `/reset-password` | публично, лимит `account` | 204 | 400 (токен), 422 (слабый пароль), 429 |
| POST | `/change-password` | вход | 204 | 422 (неверный текущий или слабый новый пароль) |

Файл: [auth.py](../backend/app/routers/auth.py). Принципы, из-за которых код выглядит так, а не проще:

- **Нельзя узнать, есть ли аккаунт.** `register` и `forgot-password` отвечают 204 при любом адресе; занятому адресу уходит письмо «аккаунт уже есть». В `register` пароль проверяется и хэшируется **до** поиска email, чтобы не отличалось и время ответа. Вход на несуществующий email сравнивает пароль с `DUMMY_PASSWORD_HASH`: Argon2 одинаково долгий в обоих случаях. Ответ всегда «Неверный email или пароль».
- **Ошибки пароля — 422 в формате FastAPI** с `loc: ["body", "password"]` (`field_error`): фронт разбирает их одной функцией и показывает текст под полем.
- **Токены из писем** (`email_tokens`): verify живёт 24 часа, reset — 1 час; в базе только sha256. Новый токен гасит прежние той же цели. `take_email_token` берёт строку `FOR UPDATE`: при двойном клике второй запрос ждёт первый и видит токен использованным. В `reset-password` токен гасится только после проверки пароля, чтобы со слабым паролем можно было исправиться той же ссылкой.
- **Письма не чаще раза в минуту и пяти в час на пользователя** (`mail_quota_left`, считается по выпущенным токенам). Лимит по email, а не только по IP: иначе чужой ящик заваливают письмами с разных адресов.
- При входе устаревший хэш Argon2 пересчитывается (`needs_rehash`): пароль известен только в этот момент.

### Бронь

| Метод | Путь | Доступ | Успех | Ошибки |
|---|---|---|---|---|
| POST | `/api/bookings` | вход + email, лимит `booking` | 201 | 400 (номер недоступен, гостей больше вместимости, промокод), 403, 404, 409 (даты заняты), 422, 429 (частота или лимит заявок) |

Файл: [bookings.py](../backend/app/routers/bookings.py). Обработчик читается сверху вниз как список условий: номер существует → доступен → вместимость → даты не заняты подтверждённой бронью → ленивая просрочка → не больше `MAX_PENDING_PER_CLIENT` (3) заявок на рассмотрении → промокод (с блокировкой строки) → `submit_booking`. Ограничители стоят в `dependencies` декоратора и выполняются раньше проверки сессии и тела, поэтому запрос с ошибкой 401 или 422 тоже расходует лимит. Просрочка идёт **до** проверки лимита и промокода: заявка с прошедшей датой заезда иначе занимала бы место в лимите и держала бы код.

Цена брони, заказа и скидка хранятся снимком, поэтому правка каталога уже сделанные брони и заказы не меняет. Услугу с заказами и акцию, применённую в бронях, удалить нельзя, только деактивировать: внешние ключи `ON DELETE RESTRICT` плюс проверка в роутере, которая отвечает понятным 409 до обращения к ограничению.

## Схемы и проверки

[schemas.py](../backend/app/schemas.py). Схемы ответов включают `from_attributes=True`, и FastAPI сериализует объекты SQLAlchemy напрямую. Всё, что видно из тела запроса, проверяет Pydantic и отвечает 422; всё, для чего нужна база, проверяет роутер и отвечает 400, 404 или 409.

| Схема | Поле | Правило |
|---|---|---|
| `StayIn` (котировка и бронь) | `check_in` | не раньше сегодняшнего дня **по часам отеля** (`hotel_time`), не дальше `MAX_LEAD_DAYS` (365) вперёд |
| | `check_out` | строго позже `check_in`; ночей не больше `MAX_STAY_NIGHTS` (30) |
| | `guests` | от 1 до 20 |
| | `promo_code` | до 32 символов; пустая строка превращается в `null` |
| `BookingCreate` | `guest_name` | 2–120 символов после обрезки пробелов |
| | `phone` | от 10 до 15 цифр, остальные символы не считаются (`validate_phone`) |
| | `comment` | до 1000 символов; из одних пробелов становится `null` |
| `RegisterIn` | `email` | в нижний регистр, шаблон `x@y.z`, до 254 |
| | `full_name` | 2–120 |
| | `consent` | только `true` |
| | `password` | политика паролей, проверяется в роутере |
| `ProfileUpdate` | `phone` | как выше; пустой — `null` |
| `ServiceOrderIn` | `quantity` | 1–20 |
| | `scheduled_at` | время без пояса считается временем отеля (так его шлёт `datetime-local`) |
| | `comment` | до 500 |
| `AdminReasonIn` | `reason` | обязателен, от 3 символов: его увидит гость |
| `RoomIn` | `price_per_night` | 1–1 000 000 |
| | `description` | не пустое, до 2000 |
| `PromoIn` | `code` | верхний регистр, `[A-Z0-9_-]{3,32}` |
| | `value` | 1–1 000 000; для процентов не больше 100 |
| | `valid_to` | не раньше `valid_from` |
| `ServiceIn` | `slug` | `[a-z0-9]+(-[a-z0-9]+)*`, до 60 |
| | `price` | 0–1 000 000 |
| `ClientUpdate` | `crm_note` | до 2000 |

Даты проверяет валидатор уровня модели, потому что правило связывает два поля. «Сегодня» берётся из `hotel_time.hotel_today()`, а не из часов сервера: контейнер работает в UTC, и в первые три часа московских суток вчерашняя дата проходила бы как сегодняшняя.

Пароли в схемах **не обрезаются** по краям: пробел — допустимый символ пароля.

## Правила брони

### Статусы и переходы

[booking_lifecycle.py](../backend/app/booking_lifecycle.py). Статус хранится в `bookings.status`: `pending`, `confirmed`, `declined`, `cancelled`. «Проживание» и «Завершена» вычисляются `display_status` из подтверждённой брони и дат и нигде не хранятся: иначе их пришлось бы переключать по расписанию, а планировщика нет.

`TRANSITIONS` — единственная таблица допустимых переходов и тех, кто их выполняет (`Actor`: `system`, `admin`, `guest`):

| Из → в | Кто |
|---|---|
| ∅ → `pending` | гость (создание заявки) |
| `pending` → `confirmed` | система, администратор |
| `pending` → `declined` | система, администратор |
| `pending` → `cancelled` | гость, администратор |
| `confirmed` → `cancelled` | гость (до дедлайна), администратор (до даты выезда) |

Нет в таблице — 409 «Это действие недоступно в текущем статусе брони». Отдельных `if status == ...` в роутерах нет.

### change_status

Единственная функция перехода. По шагам:

1. Проверяет `TRANSITIONS`. Для отмены подтверждённой брони добавляет время: гость до `check_in + время заезда отеля − FREE_CANCEL_HOURS` (48 ч), администратор до даты выезда.
2. Пишет поля брони (`status`, `reason_codes`, `reason_text`, `decided_by` или `cancelled_by/at`) и добавляет строку в журнал `booking_events`.
3. Делает `flush`. Здесь у новой брони появляется `id` для письма и срабатывает `bookings_no_overlap`; при `IntegrityError` откатывается весь запрос и отвечает 409 «Эти даты только что заняли».
4. При подтверждении создаёт задачи уборки и **отклоняет пересекающиеся заявки на рассмотрении** (причина `dates_taken`). Блокировка `SKIP LOCKED` пропускает строки, которые прямо сейчас меняет параллельный запрос: взаимных блокировок нет. Рекурсия ровно на один уровень.
5. При отмене подтверждённой брони удаляет запланированные уборки и отменяет открытые заказы услуг.
6. Ставит письмо гостю в `BackgroundTasks`.

Функция не коммитит. Почему это точка входа для всего: журнал, письма и каскады не могут разойтись со статусом, если статус нигде больше не меняется. Сид тоже создаёт брони через неё.

### Создание заявки и авто-решение

`submit_booking` собирает факты из базы (есть ли у клиента завершённое проживание, есть ли пересекающаяся заявка на рассмотрении), считает цену и вызывает `decide` из [booking_rules.py](../backend/app/booking_rules.py). Заявка всегда рождается в `pending` (событие создания, письма нет), затем при необходимости системный переход в `confirmed`/`declined`. Гость получает ровно одно письмо: об итоге.

`decide` проверяет в порядке «отказ → ручной разбор → подтверждение»: отказ первым, потому что он окончательный и причины разбора для него не нужны. Причины разбора собираются **все**, а не первая: администратор сразу видит, что проверить.

| Код причины | Условие | Результат | VIP |
|---|---|---|---|
| `client_blocked` | CRM-статус `blocked` | отклонена | — |
| `pending_conflict` | на эти даты есть другая заявка на рассмотрении | на разбор | действует |
| `long_stay` | ночей больше `AUTO_CONFIRM_MAX_NIGHTS` (7) | на разбор | не действует |
| `high_total` | сумма больше `AUTO_CONFIRM_MAX_TOTAL` (60 000 ₽), а завершённых проживаний нет | на разбор | не действует |
| `same_day` | заезд сегодня | на разбор | действует |
| `far_future` | заезд позже чем через `AUTO_CONFIRM_MAX_LEAD_DAYS` (180) | на разбор | не действует |
| `has_comment` | есть непустой комментарий | на разбор | действует |
| `auto_ok` | ни одного правила | подтверждена | — |
| `expired` | дата заезда наступила, заявку не рассмотрели | отклонена системой | — |
| `dates_taken` | пересекающуюся бронь подтвердили | отклонена системой | — |

Тексты для гостя и администратора лежат в `REASON_TEXTS` и подставляются в API и письма; в базе хранятся коды. Для заблокированного клиента текст нейтральный («свяжитесь с отелем»): гость не должен узнать о внутренней отметке, код причины видит только администратор.

**Цена.** `calculate_price` — единственный расчёт, им пользуются и котировка, и создание брони. Скидка в рублях: процентная — не больше `PROMO_MAX_PERCENT` (50 %) стоимости проживания, фиксированная — не больше самой стоимости; итог не уходит в минус. **Промокод** (`promo_refusal`, проверки по порядку): чужой персональный → отключён → ещё не начался → истёк → меньше `min_nights` → другой номер → уже занят. Чужой код проверяется первым, чтобы он не раскрывал условия акции. Код одноразовый: его держит бронь в статусе `pending` или `confirmed`, отказ и отмена код освобождают, отдельного счётчика нет. Срок действия проверяется на дату запроса, а не на даты проживания. При создании брони строка акции блокируется (`FOR UPDATE`): две параллельные брони с одним кодом идут по очереди.

## Ленивая просрочка

Планировщика в проекте нет. `expire_stale_pending` отклоняет заявки в `pending` с датой заезда раньше «сегодня по часам отеля» (причина `expired`, письмо гостю) и вызывается в начале запросов, которые показывают или меняют брони: создание заявки, списки и карточки брони гостя, отмена гостем, список, карточка и действия админки, карточка клиента. Функция идемпотентна и использует `SKIP LOCKED`.

В действиях (создание, отмена, confirm/decline/cancel) просрочка идёт **в одной транзакции** с самим действием: если действие закончится ошибкой, откатятся и статусы, и письма. В `GET` она коммитится сразу. Цена решения: статус «висит» до первого запроса, который его посмотрит; пока никто не заходит, заявка формально остаётся `pending`. Для учебного проекта это дешевле планировщика и воркера.

## Письма и фоновые задачи

[mail.py](../backend/app/mail.py) и [mail_templates.py](../backend/app/mail_templates.py). Письмо — функция шаблона, возвращающая `Mail(to, subject, html, text)`, плюс `background.add_task(send_mail, ...)`.

| Письмо | Когда | Кто ставит |
|---|---|---|
| `verify_email_mail` | регистрация, повторная отправка | `auth.py` |
| `reset_password_mail` | «забыли пароль» | `auth.py` |
| `account_exists_mail` | регистрация на занятый адрес | `auth.py` |
| `booking_review_mail` | заявка осталась на рассмотрении | `bookings.py` |
| `admin_review_mail` | то же, если задан `ADMIN_NOTIFY_EMAIL` | `bookings.py` |
| `booking_confirmed_mail`, `booking_declined_mail`, `booking_cancelled_mail` | переход в статус | `change_status` по `STATUS_MAILS` |

Три важных свойства:

- **Письмо строится сразу, а отправляется после ответа.** В `add_task` передаётся уже готовый `Mail`, пока сессия открыта и связи `room`/`user` брони доступны; `BackgroundTasks` выполняются после отправки ответа. Если запрос закончился ошибкой, задачи не запускаются, поэтому письмо не уйдёт о переходе, которого не было.
- **Ошибка доставки не ломает запрос.** `send_mail` ловит любое исключение и пишет его в лог; повторов и очереди нет (учтено в [09-tech-debt.md](09-tech-debt.md)). Если процесс упадёт между ответом и отправкой, письмо потеряется.
- **Бэкенд выбирается `MAIL_BACKEND`:** `resend` (HTTP API Resend), `console` (письмо и ссылки в лог) или `memory` (список `mail.outbox`, его читают тесты). Пустое значение выбирает `resend`, если задан `RESEND_API_KEY`, иначе `console` — поэтому в compose пустая переменная безопасна. Подключение Resend описано в [07-infrastructure.md](07-infrastructure.md).

Ссылки в письмах строятся от `APP_BASE_URL`.

## Заказы услуг и уборки

[room_service.py](../backend/app/room_service.py). Услуга — запись каталога (`category`: еда, уборка, трансфер, спа, другое; `unit`: за штуку или за проживание). Заказ можно создать к подтверждённой брони, пока проживание не завершено, на момент между заездом и выездом по часам отеля, не в прошлом; еду — только в часы `ROOM_SERVICE_HOURS` (08:00–23:00, конец не включается). Цена и итог фиксируются снимком; услуга «за проживание» всегда в количестве 1.

`ORDER_TRANSITIONS` — таблица переходов заказа по тому же принципу, что `TRANSITIONS`, и единственная точка смены его статуса `change_order_status`:

| Из → в | Кто |
|---|---|
| `new` → `accepted` | администратор |
| `accepted` → `done` | администратор |
| `new` → `cancelled` | гость, администратор, система |
| `accepted` → `cancelled` | администратор, система |

Систему используют при отмене брони: она снимает новые и принятые заказы, выполненные остаются в истории.

[housekeeping.py](../backend/app/housekeeping.py). При подтверждении брони создаётся ежедневная уборка на каждую дату **строго между** заездом и выездом и одна уборка после выезда; для проживания на одну ночь — только последняя. Гость меняет слот (утро, день, вечер, «не беспокоить») только запланированной ежедневной уборки на дату позже сегодняшней. Администратор ведёт день: `set_task_status` сознательно без таблицы переходов, чтобы можно было поправить ошибочную отметку (`done` ↔ `skipped`).

## CRM

[crm.py](../backend/app/crm.py). Показатели клиента (проживания, ночи, выручка, последнее проживание, последняя активность) считаются **одним запросом** с агрегацией по броням и нигде не хранятся: нет рассинхрона и N+1, тест `test_list_runs_constant_number_of_queries` фиксирует число запросов. «Проживание» — подтверждённая бронь с `check_out <= сегодня`. Сегмент (`new`, `guest`, `regular` от двух проживаний) вычисляется `client_segment`. Не путайте его с хранимой отметкой администратора `crm_status` (`regular`, `vip`, `blocked`): сегмент — факт, отметка — решение. Блокировка не трогает существующие брони, она влияет только на новые заявки. Поиск идёт по имени, email и телефону; телефон сравнивается по цифрам, в том числе по телефонам из броней клиента.

## Ограничение частоты

Класс `RateLimiter` в [security.py](../backend/app/security.py) хранит для каждого ключа список моментов запросов за окно и отвечает 429, когда их набралось `limit`. Ключ — IP клиента (`request.client.host`) или, при `per_client=False`, одна строка на весь сайт.

| Набор | Какие эндпоинты | Лимит по IP | Общий потолок |
|---|---|---|---|
| `booking_limiters` | `POST /api/bookings` | 5 за 10 минут | 30 за 10 минут |
| `login_limiters` | `POST /api/auth/login` | 10 за 10 минут | 30 за 10 минут |
| `account_limiters` | `register`, `resend-verification`, `forgot-password`, `reset-password` | 10 за 10 минут | 30 за 10 минут |

Четыре эндпоинта делят один счётчик `account_limiters`: все они отправляют письма или проверяют токены из писем. `verify-email` и `change-password` лимитов не имеют. Помимо IP, письма ограничены на пользователя (раз в минуту, пять в час) и заявки на клиента (3 на рассмотрении, см. выше) — это защита от спама на уровне данных, а не транспорта.

IP приходит из `X-Forwarded-For`, который ставит dev-сервер Nuxt, см. [02-architecture.md](02-architecture.md). Присланный клиентом заголовок dev-сервер пропускает как есть, поэтому лимит по IP обходится подделкой. Общий потолок от IP не зависит и ограничивает поток спама при любом заголовке. Цена потолка — атакующий может исчерпать его и на десять минут закрыть форму для настоящих гостей.

Счётчики живут в памяти процесса и обнуляются при перезапуске. Это работает, пока uvicorn запущен одним процессом (`ponytail` в коде: при нескольких воркерах нужен Redis).

## Пароли

[passwords.py](../backend/app/passwords.py). Политика по NIST SP 800-63B-4: длина от `PASSWORD_MIN_LENGTH` (15) до 128 символов после нормализации NFC и оценка `zxcvbn` не ниже 3 с учётом email, имени и слова `kivana`. Правил состава («заглавная, цифра, спецсимвол») нет намеренно: NIST их не рекомендует, они толкают к шаблонам вроде «Password1!». Причина отказа возвращается понятным текстом. Хэш — Argon2id (`argon2-cffi`). NFC нужен, чтобы «й», набранная одним символом и буквой со знаком, давала один хэш. Та же политика применяется к паролю администратора из `ADMIN_PASSWORD` и к `DEMO_PASSWORD`: если они её не проходят, сид завершится ошибкой, и backend не запустится.

## Тесты

[conftest.py](../backend/conftest.py) лежит в корне `backend/` и делает четыре вещи:

1. До первого импорта `app` подменяет `DATABASE_URL` на базу `kivana_test` и задаёт `MAIL_BACKEND=memory` и `SEED_DEMO=false`. Порядок важен: модули читают окружение при импорте. Демо-данные ломали бы остальные тесты (занятые даты, чужие клиенты).
2. Один раз на прогон создаёт `kivana_test` на том же сервере PostgreSQL, если её нет, накатывает `alembic upgrade head` и запускает `seed.main()` (справочники и администратор). База после прогона **не удаляется**, поэтому с нуля миграции проходят только на первом прогоне; на существующей базе применяются недостающие. Чтобы перепроверить с нуля, удалите базу: `docker compose exec db psql -U kivana -d kivana -c "DROP DATABASE kivana_test"`.
3. Каждый тест идёт внутри внешней транзакции, которая в конце откатывается: сессия создаётся с `join_transaction_mode="create_savepoint"`, поэтому `commit()` в коде приложения фиксирует лишь точку сохранения. Это быстрее очистки таблиц и не зависит от порядка тестов. `get_db` подменяется на эту сессию.
4. Перед каждым тестом обнуляются счётчики всех трёх наборов ограничителей и `mail.outbox`.

Фикстуры: `make_user`, `guest`, `unverified_guest`, `admin_user`, `make_booking` (бронь в нужном статусе напрямую в базе, минуя `change_status`), `client`, `guest_client`, `unverified_client`, `admin_client` (клиенты уже вошли). Один хэш пароля на все аккаунты ускоряет прогон: Argon2 намеренно медленный. Время «переводят» подменой `hotel_time.hotel_now` через `monkeypatch`, поэтому код обязан обращаться к нему как `hotel_time.hotel_today()`, а не импортировать функцию по имени.

Запуск, из каталога проекта: `docker compose exec backend pytest`. Нужны запущенные `db` и `backend`, а пользователю базы — право `CREATE DATABASE` (в контейнере `POSTGRES_USER` — суперпользователь). Сейчас **346 тестов**.
