# 07. Инфраструктура

Всё описано в [docker-compose.yml](../docker-compose.yml). Файла `.env` для запуска не требуется.

## Сервисы

| Сервис | Образ | Порт наружу | Зависит от |
|---|---|---|---|
| `db` | `postgres:16-alpine` | 5432 | — |
| `backend` | сборка из [backend/Dockerfile](../backend/Dockerfile) | 8000 | `db` в состоянии healthy |
| `frontend` | сборка из [frontend/Dockerfile](../frontend/Dockerfile) | 3000 | `backend` |

### db

Данные лежат в именованном томе `db-data`, поэтому переживают `docker compose down`, но не `down -v`.

Healthcheck опрашивает `pg_isready` каждые пять секунд, до двенадцати попыток. Именно на него ссылается условие `service_healthy` у backend — без него backend стартовал бы раньше базы и падал на первом подключении.

### backend

```yaml
command: sh -c "python seed.py && uvicorn app.main:app --reload --host 0.0.0.0"
```

Порядок обеспечивает `&&`: сначала создание таблиц и наполнение, затем сервер. Если сид завершится с ошибкой, uvicorn не запустится, и причина будет видна в логах, а не замаскирована работающим сервером с пустой базой. Отдельный entrypoint-скрипт для этого не нужен.

Строка подключения собирается в compose из тех же переменных, что получает контейнер базы, поэтому рассинхронизировать логин и пароль между сервисами невозможно.

Каталог `./backend` смонтирован в `/app`, флаг `--reload` перезапускает сервер при правке исходников.

### frontend

Монтирований два, и второе важно:

```yaml
volumes:
  - ./frontend:/app
  - /app/node_modules
```

Первое подключает исходники с хоста, но заодно перекрывает `node_modules`, установленные при сборке образа. Второе — анонимный том — возвращает содержимое образа поверх этого пути. Без него контейнер стартовал бы с пустым `node_modules`, а зависимости с хоста, даже если они там есть, собраны под другую платформу.

Переменная `API_BASE=http://backend:8000` задаёт адрес для nitro-прокси. Имя `backend` резолвится внутренним DNS сети Compose.

## Переменные окружения

| Переменная | Где задаётся | По умолчанию | Назначение |
|---|---|---|---|
| `POSTGRES_USER` | окружение или `.env` | `hotel` | Пользователь базы |
| `POSTGRES_PASSWORD` | окружение или `.env` | `hotel` | Пароль |
| `POSTGRES_DB` | окружение или `.env` | `hotel` | Имя базы |
| `DATABASE_URL` | compose | из трёх переменных выше | Строка подключения SQLAlchemy |
| `API_BASE` | compose | `http://localhost:8000` | Адрес backend для прокси |

Синтаксис `${VAR:-default}` в compose подставляет значение по умолчанию, если переменной нет. Поэтому проект поднимается сразу после клонирования, а [.env.example](../.env.example) остаётся справкой, а не обязательным шагом.

## Образы

Оба Dockerfile одностадийные и короткие — это dev-сборка, а не продакшен.

Backend: `python:3.12-slim`, установка зависимостей, копирование кода. Frontend: `node:24-alpine`, `npm ci`, копирование кода. В обоих случаях манифест копируется отдельным слоем перед исходниками, чтобы правка кода не приводила к переустановке зависимостей.

Команда `npm ci` требует `package-lock.json`, поэтому lock-файл лежит в репозитории и должен быть закоммичен. Без него сборка образа frontend упадёт. Версия Node в образе выбрана той же мажорной линейки, в которой сгенерирован lock-файл.

## Что это не покрывает

Продакшен-сборки нет: оба сервиса работают в режиме разработки с включённым автоперезапуском и без минификации. Нет reverse proxy, TLS, ограничений ресурсов, политики перезапуска и резервного копирования тома. Для учебного проекта это осознанный предел, см. [09-tech-debt.md](09-tech-debt.md).
