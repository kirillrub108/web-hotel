# 01. Обзор проекта

## Что это

Сайт гостиницы Kivana (версия 1.1) с личным кабинетом гостя и админкой. Гость выбирает номер, регистрируется, подтверждает почту и оставляет заявку на бронь. Типовую заявку система подтверждает сама, спорную оставляет администратору. Подтверждённой брони гость заказывает еду и услуги в номер и выбирает время уборки. Администратор разбирает заявки, ведёт клиентов (CRM), акции, каталог услуг, заказы, расписание уборок и номера.

Ключевой сценарий ценности: **регистрация → подтверждённая почта → заявка → авто-решение по правилам → письмо с итогом**. Весь путь проходит без звонков, а администратор тратит время только на заявки, где правила не уверены.

Дату номера закрывает только подтверждённая бронь: два подтверждённых заезда в один номер на пересекающиеся даты база не примет. Заявки на рассмотрении даты не закрывают, иначе любой мог бы занять календарь фальшивыми заявками. Если одну заявку подтвердили, пересекающиеся заявки на рассмотрении отклоняются автоматически.

Онлайн-оплаты в системе нет: услуги оплачиваются на ресепшене. Фотографий и текстов сайта через интерфейс не загрузить: данные гостиницы и каталог услуг задаются в [seed.py](../backend/seed.py), а через админку правятся цена, описание и доступность номера, услуги и акции.

## Роли

| Роль | Кто | Что может | Как входит |
|---|---|---|---|
| Посетитель | Любой без входа | Смотреть номера, услуги, контакты; считать цену в форме брони | Без входа |
| Гость | `users.role = 'guest'` | Всё, что посетитель; кабинет; бронь, если почта подтверждена | Регистрация и вход на `/login`, [auth.py](../backend/app/routers/auth.py) |
| Администратор | `users.role = 'admin'` | Всё в `/api/admin/*`: заявки, клиенты, акции, услуги, заказы, уборка, номера | Тот же `/login`; первого администратора создаёт [seed.py](../backend/seed.py) из `ADMIN_EMAIL` и `ADMIN_PASSWORD` |

Администраторы — обычные пользователи с другой ролью, а не отдельная схема входа. Интерфейса создания администраторов нет, права внутри роли не разграничены. Подробности — в [04-backend.md](04-backend.md).

## Стек и почему именно он

| Технология | Версия | Почему выбрана |
|---|---|---|
| Python | 3.12 | Аннотации типов без обратной совместимости, `StrEnum` из стандартной библиотеки |

| Alembic | 1.20 | Схема меняется миграциями, данные гостей при этом не теряются |
| Pydantic | v2 | Одни и те же классы описывают ответ API и проверку входа |
| PostgreSQL | 16 | EXCLUDE-ограничение по диапазону дат, `SELECT ... FOR UPDATE SKIP LOCKED`, массивы (`reason_codes`) |
| argon2-cffi, zxcvbn | 25.1.0, 4.5.0 | Argon2id для хэшей, zxcvbn для оценки предсказуемости по NIST SP 800-63B-4 |
| httpx | 0.28.1 | Запрос к API Resend при отправке писем |
| Nuxt | 4 | SSR из коробки, файловый роутинг, глобальный middleware, встроенный прокси в nitro |
| TypeScript | 5.9 | Типы ответов API описаны один раз в [types.ts](../frontend/app/types.ts) |
| Docker Compose | — | Три сервиса, один файл, ноль установок на хосте |

## Осознанно не взято

- **JWT.** Сессия — случайный токен в httpOnly-cookie, в БД лежит только его sha256. Сессию можно отозвать (выход, смена пароля), а с JWT пришлось бы строить список отзыва.
- **Многофакторная аутентификация и разграничение прав сотрудников.** Пароль длиной от 15 символов — единственный фактор; администратор имеет все права. Это следствие NIST SP 800-63B-4: длинный пароль без второго фактора допустим.
- **Планировщик и очередь задач.** Просрочка заявок ленивая ([booking_lifecycle.py](../backend/app/booking_lifecycle.py), `expire_stale_pending`), письма уходят из `BackgroundTasks`. Цена: у писем нет повторных попыток, при перезапуске между сохранением и отправкой письмо потеряется.
- **Репозитории и слой сервисов для всего подряд.** Роутеры обращаются к SQLAlchemy напрямую; в отдельные модули вынесено только то, что нужно в нескольких местах или проверяется без HTTP: правила брони, переходы статусов, CRM-запросы, промокоды, заказы, уборки.
- **Онлайн-оплата.** Услуги оплачиваются на ресепшене; итог по брони считается только для показа ([room_service.py](../backend/app/room_service.py), `services_total`).
- **CORS-middleware.** Не нужен: браузер и SSR ходят на тот же origin, см. [02-architecture.md](02-architecture.md).
- **Redis.** Счётчики ограничения частоты живут в памяти процесса. Этого хватает, пока uvicorn работает одним процессом.
- **Продакшен-сборка и reverse proxy.** Проект запускается в dev-режиме; см. [07-infrastructure.md](07-infrastructure.md) и [09-tech-debt.md](09-tech-debt.md).
- **Tailwind и UI-киты.** Один файл [main.css](../frontend/app/assets/css/main.css) с переменными плюс scoped-стили компонентов.

## Вопросы на понимание

1. Почему заявка на рассмотрении не закрывает даты, а подтверждённая закрывает, и что происходит с пересекающимися заявками при подтверждении? (Иначе любой мог бы занять календарь заявками; пересекающиеся pending отклоняются системой с кодом `dates_taken`. См. [03-runtime-flows.md](03-runtime-flows.md).)
2. Что гарантирует отсутствие двойной брони, если два администратора одновременно подтвердят пересекающиеся заявки? (Ограничение `bookings_no_overlap` в базе, см. [05-data-model.md](05-data-model.md).)
3. Кто может создать бронь и какой код получит гость с неподтверждённой почтой? (Только гость с `email_verified_at`; без подтверждения — 403 из `require_verified_user`.)
4. Где задаётся первый администратор и что будет, если его пароль не проходит политику паролей? (`ADMIN_EMAIL`, `ADMIN_PASSWORD` в [seed.py](../backend/seed.py); сид завершается с ошибкой, uvicorn не стартует. См. [07-infrastructure.md](07-infrastructure.md).)
