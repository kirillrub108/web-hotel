# unik-report — заполнение отчётов САФУ по шаблону

Цель — взять шаблон отчёта (КР / ЛП / ЛР), изучить требования из контекста проекта
(методические указания, варианты заданий, исходные данные) и выдать готовый .docx,
наполненный содержанием, при этом **точно соблюдая стилевое оформление шаблона**.

## Что меняется и что нет

В шаблонах САФУ от работы к работе меняется ТОЛЬКО титульный лист и содержание
разделов. Всё остальное (стили текста, заголовков, подписей, нумерации,
колонтитулов, оглавления) подчинено единому корпоративному стандарту СТО САФУ
и уже задано внутри файла .docx. Поэтому скилл:

- **Никогда не трогает титульный лист** — он уже заполнен пользователем.
- **Никогда не определяет новые стили** — все нужные `styleId` уже есть в шаблоне.
- **Использует существующие стили шаблона по их СМЫСЛОВОМУ НАЗВАНИЮ**, а не по
  идентификатору (идентификаторы вроде `a4`, `ad`, `ac` различаются между файлами).

## Алгоритм работы

### Шаг 0. Источник шаблона

1. Если пользователь приложил .docx в текущее сообщение — это шаблон.
2. Если приложений нет — поискать .docx среди вложений последних сообщений и
   в `/mnt/user-data/uploads/`. Если ничего — спросить, какой шаблон взять.
3. Скопировать шаблон в `/home/claude/template.docx` (read-only исходник трогать
   нельзя).

### Шаг 1. Анализ шаблона

Запустить:

```bash
python3 scripts/analyze_template.py /home/claude/template.docx /home/claude/unpacked
```

Скрипт распакует docx и выведет JSON-отчёт со следующими полями:

- `kind` — тип работы: `kr` (контрольная), `lp` (лаб. практикум), `lr` (отдельная
  ЛР) или `unknown`. Определяется эвристически по тексту титульного листа.
- `discipline` — название дисциплины (если найдено).
- `task_text` — текст «ЗАДАНИЯ» (если есть отдельный раздел задания).
- `existing_outline` — массив объектов `{level, text, anchor_xml_id}` с уже
  существующими заголовками. Для КР это обычно номера разделов «1 …», «2 …»,
  «Заключение». Для ЛП — «Лабораторная работа №1», «Часть 1.1» и т.д.
- `existing_captions` — массив существующих подписей к рисункам/таблицам/
  листингам с указанием их места в документе.
- `style_map` — словарь: смысловая роль → `styleId` шаблона. Скилл ВСЕГДА
  использует этот словарь, не зашивая идентификаторы. См. ниже.
- `numbering` — словарь номеров автонумерации по ролям (нужно, чтобы листинги
  и подписи продолжали правильный счётчик).
- `unpacked_dir` — папка с распакованным XML для последующего редактирования.

`style_map` содержит как минимум следующие смысловые роли — точный набор
зависит от шаблона. Если какой-то роли в шаблоне физически нет, скрипт
вернёт `null` — это означает, что её надо реализовать через прямое
форматирование run/paragraph, без `pStyle`.

| Роль | Что это |
|------|---------|
| `heading_1` … `heading_4` | Заголовки уровней 1–4 (для разделов и подразделов) |
| `structural` | «Структурный элемент» — ОГЛАВЛЕНИЕ, ВВЕДЕНИЕ, ЗАКЛЮЧЕНИЕ, СПИСОК ИСТОЧНИКОВ |
| `figure_body` | Абзац-контейнер для самого рисунка (центрированный, без отступа) |
| `figure_caption` | «Подпись к иллюстрации» / «Подпись к рисункам» |
| `listing_body` | Стиль листинга (моноширинный шрифт, Courier New) |
| `listing_caption` | «Подпись к листингу» |
| `table_caption` | «Подпись к таблице» |
| `table_header` | «Заголовок таблицы» |
| `formula` | Стиль абзаца для формулы |
| `bullet_list` | Маркированный список (List Bullet) |
| `numbered_list` | Нумерованный список (Перечисление) |
| `references_list` | Список использованных источников |
| `body` | Обычный текст (Normal) |
| `toc` | TOC 1/2/3 (только если нужно перестроить оглавление) |

Перед любой генерацией контента обязательно прочитать вывод `analyze_template.py`
и держать `style_map` под рукой — каждый сгенерированный блок XML должен
ссылаться на стиль через смысловую роль.

### Шаг 2. Сбор материалов из проекта

Изучить контекст проекта через `project_knowledge_search`. Что искать:

- **Методические указания** — обычно лекция/методичка по дисциплине. Из них
  берётся теоретическая основа разделов (но не копируется дословно — кратко
  пересказывается своими словами с привязкой к выполняемому варианту).
- **Задание / вариант** — таблица или текст «Вариант N: данные / задание».
  Если в самом шаблоне в тексте задания указан номер варианта или конкретные
  данные — ориентироваться на них. Иначе попросить пользователя уточнить
  вариант, прежде чем что-либо генерировать.
- **Исходные данные** — таблицы, CSV/XLSX, графики, которые нужно посчитать
  или проанализировать.
- **Требования СТО САФУ** — могут быть в проекте, могут отсутствовать. Если
  отсутствуют — пользоваться `references/sto-safu-rules.md`.

Если в проекте обнаружено сразу несколько вариантов задания, а в шаблоне номер
варианта не указан — **остановиться и спросить**. Не угадывать вариант.

### Шаг 3. Планирование наполнения

Прежде чем генерировать XML, выписать (в чате, кратко) **план отчёта**:

1. Список разделов в порядке их следования (либо уже зафиксированных в
   `existing_outline`, либо вновь предложенных, если шаблон пустой).
2. Для каждого раздела:
   - что войдёт в текст;
   - какие формулы выводятся (и какая ключевая формула получается в итоге);
   - какие будут таблицы (с реальным содержанием по варианту);
   - какие будут листинги/код (с фактическим кодом, а не заглушкой);
   - какие рисунки нужны и **почему именно они нужны** — если рисунок не
     добавляет ничего нового к тексту, его не должно быть.
3. Заключение: что показал отчёт по итогу (1–2 абзаца с конкретными выводами
   из расчётов, не общими фразами).

Этот план показывается пользователю до сборки. Если он одобряет — двигаемся
дальше; если у него правки — учитываем их и пересобираем план.

### Шаг 4. Генерация контента

На этом этапе для каждого пункта плана подготовить готовые тексты на русском:

- **Тексты разделов** — связный академический русский, без воды, со ссылками
  на формулы/таблицы/рисунки в форме «по формуле (3)», «согласно таблице 2»,
  «как видно из рисунка 5». Нумерация ставится автоматически за счёт стиля
  подписи (см. ниже), поэтому в тексте достаточно подставлять номер в скобках.
- **Формулы** — в виде линейного текста с использованием Unicode-символов:
  `x̄ = Σxᵢ/n`, `σ² = Σ(xᵢ − x̄)²/n`, `χ² = Σ(mᵢ − m'ᵢ)²/m'ᵢ`. Office Math
  на текущем этапе не генерируем (это требует отдельной библиотеки и не
  поддерживается всеми просмотрщиками). Текст формулы центрируется стилем
  `formula` из шаблона.
- **Таблицы** — содержат фактические числа варианта. Заголовки колонок —
  отдельный ряд, ниже подпись «Таблица N — …».
- **Листинги** — реальный код (Python/SQL/Excel-формула — в зависимости от
  дисциплины), отформатированный аккуратно: 4 пробела, без табуляций.

### Шаг 5. Конструирование XML

Использовать библиотеку `scripts/build_blocks.py`:

```python
from build_blocks import BlockFactory, load_style_map

style_map = load_style_map('/home/claude/style_map.json')
b = BlockFactory(style_map)

xml_chunks = [
    b.structural('ВВЕДЕНИЕ'),
    b.paragraph('Цель работы — изучить …'),
    b.heading(1, 'Теоретическая часть'),
    b.paragraph('…'),
    b.formula('χ² = Σ (mᵢ − m\'ᵢ)² / m\'ᵢ', number=1),
    b.heading(2, 'Расчёт основных характеристик'),
    b.table(
        caption='Расчёт частот и накопленных частостей',
        headers=['№','xᵢ','wᵢ'],
        rows=[[1,'1.218','0.04'], …],
    ),
    b.figure_placeholder('Гистограмма распределения частот', height_cm=8),
    b.figure_caption('Гистограмма распределения'),
    b.listing(
        caption='Код для вычисления χ²-критерия',
        code='import numpy as np\n…',
        language='python',
    ),
    b.structural('ЗАКЛЮЧЕНИЕ'),
    b.paragraph('…'),
]
```

Все функции возвращают строку XML без объявления namespace — её просто
склеивают и вставляют в `document.xml` шаблона.

`b.figure_placeholder(description, height_cm=8)` создаёт центрированную
рамку фиксированной высоты с текстом «[Место для рисунка: <описание>]».
Это сигнал пользователю, куда вставить настоящий скриншот. Подпись
ставится отдельным вызовом `figure_caption` — нумерация Word'а
проставится автоматически (стиль подписи имеет numId).

`b.listing(caption, code)` — **комбинированный** метод: подпись к
листингу ставится сверху, а сам код заворачивается в таблицу 1×1 с
тонкой чёрной рамкой (визуально выделяет код среди прочего текста).
Не вызывай `listing_caption(...)` руками вокруг кода — `listing()`
уже это делает.

`b.table(caption, headers, rows)` — тоже **комбинированный**: подпись
к таблице ставится сверху, под ней — сама таблица. Не вызывай
`table_caption(...)` руками вокруг `table(...)`.

ВАЖНО про порядок подписей (по СТО САФУ):
- **Рисунок** → подпись СНИЗУ: сначала `figure_placeholder`, потом
  `figure_caption`.
- **Таблица** → подпись СВЕРХУ: используй `b.table(caption='...', …)`,
  и не парься о порядке.
- **Листинг** → подпись СВЕРХУ: используй `b.listing(caption='...', …)`,
  и не парься о порядке.

ВАЖНО: НИКОГДА не писать вручную «Рисунок 1 —», «Листинг 3 —», «Таблица 2 —».
Эти префиксы добавляются Word'ом автоматически из настроек нумерованных
стилей. Передавать в `*_caption()` только смысловое название.

ВАЖНО: каждый заголовок 1-го уровня (`heading(1, …)`) и каждый
структурный элемент (`structural(…)` — ВВЕДЕНИЕ, ЗАКЛЮЧЕНИЕ, СПИСОК
ИСПОЛЬЗОВАННЫХ ИСТОЧНИКОВ, ПРИЛОЖЕНИЕ) автоматически начинаются с новой
страницы (атрибут `<w:pageBreakBefore/>`). Руками `b.page_break()`
перед ними ставить не нужно.

### Шаг 6. Вставка контента в шаблон

```bash
python3 scripts/insert_into_doc.py \
  --unpacked /home/claude/unpacked \
  --plan /home/claude/plan.json \
  --content /home/claude/content.xml \
  --output /home/claude/filled.docx
```

Скрипт сделает следующее:

1. Определит, где в `document.xml` шаблона заканчивается заголовочная часть
   (титульный лист, лист задания/замечаний, оглавление) и начинается тело
   отчёта.
2. **Не трогая** ничего выше точки начала тела, вставит сгенерированный XML
   на место текущего «болванчика» (для КР это обычно одинокие подписи
   рисунков, оставшиеся от старой работы; для ЛП — заголовки лабораторных
   с подписями без содержания).
3. Если тело уже частично заполнено и пользователь просил «дополнить»
   (а не «пересоздать»), скрипт идёт по разделам и вставляет недостающее
   содержание в нужные места, не дублируя уже имеющееся.
4. Запакует обратно через `pack.py` с валидацией.

### Шаг 7. Финальная проверка

После сборки прогнать валидатор:

```bash
python3 /mnt/skills/public/docx/scripts/office/validate.py /home/claude/filled.docx
```

Если валидатор ругается — посмотреть, что именно сломано, исправить
исходный XML и пересобрать. Самые частые причины:

- **Нарушен порядок дочерних элементов в `<w:pPr>`**. По схеме OOXML
  порядок строгий: `pStyle → numPr → tabs → spacing → ind →
  contextualSpacing → jc → outlineLvl → rPr`. Если генерируешь XML
  руками — используй именованные параметры `_ppr(...)` из
  `build_blocks.py`, а не склеивай строку. Самые коварные пары:
  spacing ОБЯЗАТЕЛЬНО до ind, ind до jc, jc до outlineLvl. Если
  поменять местами — Word файл откроет, но `validate.py` ругнётся,
  и часть LibreOffice/Pages корректно отрисовать не сможет.
- **Тело отрезано внутри `<w:sdt>`**. Оглавление в шаблонах САФУ часто
  обёрнуто в Content Control (`<w:sdt>...</w:sdt>`); `find_body_start`
  это уже учитывает, но если вмешиваешься руками — проверь баланс.
- Пустые `<w:t>`-элементы с пробелами без `xml:space="preserve"` — починит
  авто-репейр `pack.py`.
- Незакрытые `<w:p>` — проверить, что каждый блок из `build_blocks.py`
  заканчивается на `</w:p>` (или `</w:tbl>` для таблиц).
- Битые ссылки на нумерацию — `numId`, которого нет в `numbering.xml`.
  Все смысловые подписи (figure/listing/table) опираются на нумерацию,
  которая уже есть в шаблоне; ничего нового создавать не нужно.

Затем презентовать результат пользователю через `present_files`.

## Адаптация под тип работы

### КР (контрольная)

- Структура: Введение → задания 1..N → Заключение → Список источников.
- Каждое задание — отдельный раздел `heading_1`. Внутри — подзадачи через
  `heading_2`.
- Если в задании написано «решить N вариантов» — каждый вариант оформить
  как `heading_2`, а сам ход решения — обычным текстом с формулами.
- В конце обязательно «ЗАКЛЮЧЕНИЕ» как `structural`.

### ЛП (лабораторный практикум)

- Структура: Лабораторная работа №1 → Лабораторная работа №2 → …
- Каждая ЛР — `heading_1` с названием «Лабораторная работа №N. <Тема>».
- Внутри ЛР — её части/пункты как `heading_2` («Часть 1.1 — …», «2.1 …»).
- Обычно содержит много рисунков-скриншотов; для каждого ставится
  плейсхолдер с осмысленной подписью.
- Заключения у ЛП обычно нет.

### ЛР (отдельная лабораторная работа)

- Структура: Цель работы → Задание → Ход работы → Выводы.
- Одна работа — никаких «Лабораторная работа №N» сверху.
- «Цель работы», «Задание», «Выводы» — `structural`. «Ход работы» — текст с
  подразделами.

## Когда нужен рисунок, а когда нет

Рисунки оставлять только если они **существенно** поясняют ход работы:

- Скриншот интерфейса — да, если задание требует выполнить шаг в конкретном
  ПО («зарегистрироваться», «настроить процесс», «создать документ»).
- Гистограмма, полигон, кумулята, корреляционное поле — да, если расчёт
  предполагает построение графика как итог.
- График функции, схема алгоритма — да, если задание про них.

Не вставлять:

- Картинку «общая схема СЭД» в виде красивой инфографики — это вода.
- Иллюстрацию к теоретическому абзацу, если её нет в требованиях.
- Декоративные изображения «для красоты».

Если сомнительно — НЕ ставить плейсхолдер. Пустое место лучше лишнего
плейсхолдера, на который пользователю придётся искать содержимое.

## Соглашения и привычки СТО САФУ

Подробности — в `references/sto-safu-rules.md`. Ключевое:

- Times New Roman 14, 1.5 интервал в основном тексте — это уже в шаблоне.
- Поля 30/20/20/20 мм — это уже в шаблоне.
- Заголовки разделов — заглавными, по центру или по ширине (в зависимости
  от шаблона); ничего ручного не нужно — `heading_1` сделает.
- Подпись к рисунку — снизу, формат «Рисунок N — Название», точка в конце
  НЕ ставится. Нумерация автоматическая.
- Подпись к таблице — сверху, формат «Таблица N — Название».
- Подпись к листингу — сверху, формат «Листинг N — Название».
- Формулы нумеруются справа в круглых скобках: `(1)`, `(2)`. Это делается
  через табуляцию в стиле `formula` — см. функцию `b.formula(text, number=N)`.

## Чего НЕ делать

- Не редактировать титульный лист, не «улучшать» ФИО/группу/руководителя —
  даже если кажется, что там опечатка.
- Не определять новые стили в `styles.xml`. Если в шаблоне нет роли — она
  реализуется ручным форматированием абзаца, без `pStyle`.
- Не вставлять «Рисунок 1 —» руками в подпись. Только смысловое название.
- Не копировать длинные куски методички. Краткий пересказ + ссылка через
  список источников.
- Не использовать `\n` в тексте. Каждый абзац — отдельный вызов `paragraph()`.
- Не вставлять Office Math (`<m:oMath>`) без острой необходимости — он
  плохо рендерится в LibreOffice/Google Docs. Формулы — линейным текстом
  в стиле `formula`.
- Не использовать unicode-буллеты `•` или `–` руками — только через стиль
  `bullet_list` / `numbered_list`.
- Не плодить плейсхолдеры рисунков. См. правило «когда нужен рисунок».

## Краткая шпаргалка по командам

```bash
# 1. Распаковка + анализ
python3 scripts/analyze_template.py <template.docx> <unpacked_dir>
# → пишет style_map.json, plan_skeleton.json в <unpacked_dir>/..

# 2. Сборка контента (на стороне Claude, не скрипта):
#    собрать xml_chunks из BlockFactory, записать в content.xml

# 3. Вставка
python3 scripts/insert_into_doc.py \
  --unpacked <unpacked_dir> \
  --content content.xml \
  --output filled.docx \
  [--mode replace|append]
# replace — заменяет тело отчёта (всё после оглавления/листа замечаний);
# append  — дописывает в конец (полезно когда часть уже сделана вручную).

# 4. Валидация
python3 /mnt/skills/public/docx/scripts/office/validate.py filled.docx
```

После успешной сборки — `present_files(['filled.docx'])`.
